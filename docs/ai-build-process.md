# 跟一口：AI 协作开发记录

## 这份记录说明什么

“跟一口”采用 AI 辅助编程完成工程实现，但产品并不是由一次 Prompt 自动生成。整个过程更接近一个持续迭代的小型产品团队：人负责定义问题、约束体验和作出最终判断，AI 负责加速方案拆解、代码实现、调试、测试和文档整理。

## 协作边界

### 人负责的部分

- 从真实生活场景中提出“朋友喝水带动我喝水”的产品假设。
- 明确不做饮水目标、排名、连续签到和未完成惩罚。
- 绘制杯子、图标和产品视觉，决定页面信息层级与动效感受。
- 区分「我喝了」与「跟一口」的行为语义，并持续修正规则。
- 在手机、平板和安装后的 PWA 中验收体验。
- 发布内容、接收用户反馈，并结合聚合数据决定迭代优先级。

### AI 协助的部分

- 把自然语言产品规则拆成前端状态、接口、数据库结构和测试场景。
- 编写与重构客户端、Vercel Functions、邮件登录和 Web Push 代码。
- 根据复现现象定位跨端显示、缓存、会话和实时状态问题。
- 将反复出现的缺陷沉淀为自动化测试。
- 整理产品文档，对匿名聚合数据和公开评论做辅助分析。

## 四个有代表性的迭代

### 1. 从“提醒”改成“行为信号”

早期最容易把产品理解为另一个喝水提醒工具。迭代后将核心模型明确为：用户先在现实中喝水，再点击「我喝了」发送一次真实行为；朋友的「跟一口」只完成回应，不继续制造新一轮提醒。

这条规则同时影响了按钮文案、服务端数据结构、通知内容和状态页展示，因此先在产品文档中确定，再进入代码实现。

### 2. 从单状态页改成按时间处理消息

当“朋友刚喝了”和“朋友刚回应我”同时出现时，固定优先级会让另一条信息被覆盖。后来改为按时间进入队列：用户完成一个动作后，马上展示剩余消息；结果状态由用户主动返回主页，不再被轮询强制切走。

### 3. 选择性回应由前后端共同约束

长按「跟一口」选择回应对象时，曾出现未勾选成员也被回应的问题。修复不只调整界面选择状态，同时让服务端只接受本次有效目标，避免客户端状态错误直接污染关系数据。

### 4. 从浏览器原型走向可安装 PWA

公开使用后暴露了 Android 安装入口、iPhone 独立模式会话、系统安全区、字体加载、Service Worker 刷新和通知权限等问题。每一项都需要在真实设备上复现，无法只凭桌面浏览器判断。

## 验证方式

- 20 次版本提交记录了从可运行 MVP 到生产版本的演进。
- 9 个自动化测试文件覆盖页面渲染、邮箱登录、邀请关系、喝水轮次、选择性回应、杯子编辑、成员设置、数据持久化和 Vercel API。
- 公开上线后，通过匿名聚合数据库指标和用户评论交叉判断主要断点。
- 数据只用于描述行为，不把同期增长直接解释为因果关系。

## 主要反思

1. AI 可以很快做出页面，但复杂产品真正困难的是状态语义和边界一致性。
2. 一个问题第二次出现时，就应该考虑用测试或明确的状态表固定预期。
3. PWA 的安装、推送、Cookie 和字体必须在真实设备与生产域名中验证。
4. 邮件额度、数据库区域和网络可达性同样属于产品体验，而不仅是工程配置。
5. 公开传播前应先接入来源与关键漏斗埋点，否则只能可靠描述同期变化，无法准确计算渠道转化。

## 下一轮会怎么做

- 先补齐访问来源、注册、建联、通知授权和核心互动的事件漏斗。
- 优先修复创建关系后没有第二个人加入的主要断点。
- 在不引入打卡压力的前提下，小范围验证历史记录等需求。
- 继续把产品决策、代码变化、测试证据和用户结果放在同一条迭代链路里。
