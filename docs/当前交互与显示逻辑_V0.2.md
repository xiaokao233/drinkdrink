# 跟一口：当前交互与显示逻辑 V0.2

更新日期：2026-09-05  
用途：记录线上版本的真实行为，作为后续调整页面、接口与测试时的统一依据。

## 1. 产品里的三层状态

页面显示由三层状态共同决定：

1. **主分区**：喝水、关系、个人。
2. **主分区内的状态**：喝水首页包含平静、我喝了、他们刚喝了、我已跟随、有人跟随五种状态。
3. **独立流程页**：登录、设置杯子、安装、通知、创建／加入关系、关系详情、账户设置等。独立流程页显示时会覆盖主分区内容。

除登录、开始、首次设置身份和注销完成页外，中间流程页都提供“返回”和“首页”两个出口。底部导航只在三个主分区显示。

## 2. 喝水首页的完整状态机

```text
平静 calm
  ├─ 点“我喝了” ───────────────→ 已发送 sent
  └─ 收到朋友新的喝水信号 ─────→ 待回应 incoming

待回应 incoming
  ├─ 轻点“跟一口” ─────────────→ 已跟随 followed（回应全部当前对象）
  ├─ 长按“跟一口” ─────────────→ 选择对象 selector
  │    ├─ 勾选／取消 ───────────→ 保持在选择对象
  │    ├─ 再点“跟一口” ────────→ 已跟随 followed（只回应勾选对象）
  │    └─ 取消选择 ─────────────→ 待回应 incoming
  ├─ 点“我喝了” ───────────────→ 已发送 sent
  └─ 点“回到首页” ─────────────→ 平静 calm

已发送 sent
  ├─ 有人回应这一口 ───────────→ 有人跟随 responded
  ├─ 点“我喝了” ───────────────→ 新一轮已发送 sent
  └─ 点“回到首页” ─────────────→ 平静 calm

已跟随 followed / 有人跟随 responded
  ├─ 点“我喝了” ───────────────→ 已发送 sent
  └─ 点“回到首页” ─────────────→ 平静 calm
```

### 2.1 平静 `calm`

- 主按钮是“我喝了”。
- 有有效关系且允许发送时，这一口会发送给关系中的朋友；否则只显示为自己的喝水反馈。
- 收到新的朋友信号后进入“他们刚喝了”。

### 2.2 已发送 `sent`

- 点击后立刻在本地切换，以免用户等待网络。
- 一秒内的重复点击会被拦截；动画结束后再次点击代表新一轮喝水。
- 该状态不会因为五秒同步自动退回首页，只能由用户主动返回或被更高优先级的新事件替换。

### 2.3 待回应 `incoming`

- 横向显示当前仍未回应的朋友，每人只显示最近一条信号。
- 时间缺失或无效时统一显示“刚刚”，不会显示 `undefined`。
- 轻点“跟一口”回应全部当前可回应对象。
- 长按进入选择模式，初次打开时默认全选；之后的取消勾选会一直保留到确认或取消。
- 选择模式打开期间，五秒同步和新推送可以更新名单，但不能关闭选择面板、切换页面或重新勾选用户；新到达的人默认不勾选。
- 确认时前端只提交仍被勾选且当前仍有效的用户 ID，服务端也只向这些用户写入回应并发送推送。

### 2.4 已跟随 `followed`

- 显示本次实际回应的人，不再引用同步后的全量名单。
- 保持显示，直到用户点“我喝了”或“回到首页”。

### 2.5 有人跟随 `responded`

- 显示实际回应了自己的朋友。
- 不自动退回首页；用户点“回到首页”后把这一批回应标记为已看过。
- 同一批回应不会再次把界面弹回来，新的回应仍会再次进入该状态。

## 3. 自动显示优先级

仅当用户位于“喝水”主分区、没有打开独立流程页、也没有正在选择回应对象时，后台同步才允许自动切换首页状态。

当前优先级为：

| 优先级 | 条件 | 显示结果 |
| --- | --- | --- |
| 1 | 有一批尚未看过的新回应 | 有人跟随 `responded` |
| 2 | 有尚未忽略、尚未回应的朋友信号 | 待回应 `incoming` |
| 3 | 原来在待回应，但信号已全部处理 | 平静 `calm` |
| 4 | 没有新事件 | 保持用户当前看到的状态 |

系统推送在页面前台到达时会先拉取云端数据。普通状态下，喝水推送进入“待回应”，回应推送进入“有人跟随”；关系推送只更新数据，不强制打断当前页面。选择对象期间任何推送都只同步数据，不打断操作。

## 4. 登录与首次使用

| 当前页面 | 用户操作 | 成功后 | 失败／跳过 |
| --- | --- | --- | --- |
| 登录 | 输入邮箱并发送验证码 | 显示验证码输入 | 显示具体错误，可重试 |
| 验证码 | 输入六位验证码 | 老用户进入首页；新用户进入“开始” | 验证码错误或过期时留在本页 |
| 开始 | 选择创建关系／输入邀请码 | 进入设置身份，并记录后续方向 | — |
| 我的杯子 | 设置名称、杯型与配色 | 云端保存后进入安装 | 保存失败时不离开 |
| 添加到桌面 | 一键安装或继续用浏览器 | 进入通知 | 不支持一键安装时显示真实浏览器步骤 |
| 开启通知 | 允许通知 | 完成设备订阅，进入创建／加入关系 | “以后再说”会关闭三类通知并继续 |

登录会话保存在安全 Cookie 中。安装版和浏览器版是否共用现有登录，最终仍受手机系统与浏览器对 PWA Cookie 的处理方式影响。

## 5. 关系交互

### 5.1 创建关系

1. 输入关系备注。
2. 服务端创建关系和唯一邀请码。
3. 进入“等待加入”，复制按钮只复制纯邀请码。
4. 用户可直接“完成并进入”，关系以待加入卡片保留。
5. 朋友输入邀请码并确认后，双方云端关系更新，创建者收到关系通知。

### 5.2 加入关系

1. 输入邀请码，或打开 `/join/邀请码` 链接。
2. 服务端验证邀请码并返回现有成员预览。
3. 接受后加入关系并进入关系分区；拒绝则返回上一步。
4. 自己输入自己的邀请码时不允许加入。

### 5.3 关系详情

- 修改关系备注：只改变自己看到的备注，并同步到云端。
- “接收这段关系的信号”：控制朋友的“我喝了”是否会发给自己。
- “向这段关系发送信号”：控制自己的“我喝了”是否发给这段关系。
- 退出关系：云端删除自己的成员关系；无人剩余时清理整个关系。
- 创建者尚未等到成员加入时，可以取消邀请。

### 5.4 仍属于原型的关系功能

“邀请新成员需要现有成员共同确认”的提案、同意、拒绝、撤回页面目前只有本地演示逻辑，没有对应的云端表和接口。它不应被当作已上线功能。

## 6. 个人与设备设置

| 功能 | 当前真实行为 |
| --- | --- |
| 编辑杯子 | 杯型和配色保存到云端，其他设备登录后可同步 |
| 安装到桌面 | Android Chrome 支持时调用真实系统安装框，否则展示手动步骤 |
| 通知 | 一键申请系统权限、创建推送订阅并保存到云端；每台设备单独设置 |
| 通知分类 | 喝水、回应、关系三类偏好会随该设备的推送订阅保存 |
| 数据说明 | 说明账号、关系与通知数据用途 |
| 退出登录 | 清除本设备会话，并移除本设备推送订阅 |
| 注销账户 | 多次确认后删除云端账户及关联数据，不可恢复 |

## 7. 云端数据与本地状态边界

| 数据 | 保存位置 | 多设备是否一致 |
| --- | --- | --- |
| 账户、杯子、关系、邀请码 | Neon 云数据库 | 是 |
| 喝水事件与回应 | Neon 云数据库 | 是 |
| 关系级接收／发送开关 | Neon 云数据库 | 是 |
| 推送订阅和通知分类 | 云端按设备保存 | 每台设备可不同 |
| 单个成员的备注、接收／发送开关 | 浏览器本地 | 否 |
| 当前正在看的首页状态 | 页面内存 | 否 |
| 已看过的回应、已忽略的喝水事件 | 浏览器本地存储 | 否 |
| 安装状态、系统通知权限 | 手机系统／浏览器 | 每台设备不同 |

因此手机和平板可能对同一旧信号显示不同结果：喝水数据一致，但“这台设备是否已经看过／略过”目前是本地记录。

## 8. 当前已确认的逻辑风险

以下不是本次勾选 Bug，而是梳理后需要下一轮确认的产品规则：

1. **喝水信号有效期过长**：服务端目前把未回应信号保留 24 小时，而回应反馈只保留 30 分钟。24 小时会让“他们刚喝了”显得不像即时状态，建议改为 30～60 分钟。
2. **新回应高于新喝水**：两者同时存在时优先显示“有人跟随”。需要确认是否符合产品语气，或改成按最新发生时间决定。
3. **已读状态不跨设备**：手机点过“回到首页”后，平板仍可能显示同一事件。若希望完全一致，需要把已读状态写入数据库。
4. **成员级开关只在本机生效**：关系级开关是真实云端规则，成员详情里的单人开关目前只是本地过滤，换设备会丢失。
5. **同一人的多条未回应信号被合并显示**：页面只显示最近一条，但回应这个人时服务端会一并结束其所有未回应事件。界面应继续保持“按人回应”的概念，或改为明确的一轮一条。
6. **添加成员共同确认仍是演示**：如果下一阶段需要正式多人关系，必须先补数据模型和服务端接口。

## 9. 下一轮推荐处理顺序

1. 把喝水信号有效期从 24 小时调整到产品确认的时长。
2. 明确“新回应”和“新喝水”同时出现时的显示规则。
3. 决定已读／忽略状态是否需要跨设备同步。
4. 统一关系级和成员级接收／发送规则，避免两个开关含义重叠。
5. 再决定是否正式开发多人邀请确认流程。

本轮已经完成：选择回应对象时，后台同步或前台推送不会重新勾选未选择的人，也不会打断正在进行的选择；确认请求只携带实际勾选对象。
